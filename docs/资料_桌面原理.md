# 荣耀桌面 14 / 17 —— SwipeUp 返家动画（合并 MotionEngine 后的完整梳理）

## 0. 总结论

| | V14 (14.0.0.262) | V17 (17.0.20.191) |
|---|---|---|
| 经典路径（每轴独立 `SpringInterpolator`） | ✅ 唯一路径 | ✅ 原样保留，spring 常量一个没改 |
| Motion 引擎路径（物理求解器） | ❌ 无 `MotionController` / `sIsUseMotionEngine` / `CloseAnimSceneManager`（grep 命中 0） | ✅ 新增，`sIsUseMotionEngine` 为真时接管 |
| 横纵阻尼不同 | ✅（只在位移/卡片通道） | ✅ 经典路径相同；**Motion 路径下横纵共用一个标量** |
| scale 有速率传递 | ✅ 经典路径本来就有 | ✅ 经典路径同；**Motion 路径下由同一 MotionObject 的线速度天然耦合** |

> 之前说的“17 改了横纵阻尼 / 加了 scale 速率传递”，准确表述是：**17 不是改了老路径，而是新增了一条物理引擎路径；开了这条路径才表现出“阻尼统一 + scale 跟速度”**。

### 4.2 速度与耦合（这是“scale 有速率传递”的真正来源）

```java
// MotionController.refreshReturnMotionInfo :2152-2163
mWindowObject.setPivotX(screenW*0.5f); mWindowObject.setPivotY(screenH*0.5f);
mWindowObject.setScaleX(rectF.width()/screenW);
mWindowObject.setScaleY(rectF.height()/screenH);
mWindowObject.setX(rectF.centerX() - screenW*0.5f);
mWindowObject.setY(rectF.centerY() - screenH*0.5f);

mVelocityX = mHnLauncherSwipeHandlerV2.getTransSpeedX();
if (screenH - rectF.bottom == 0)
    mVelocityY = -getTransSpeedY() * (getCurrentDisplacement() / mLinearDragLength);
else
    mVelocityY = -getTransSpeedY() * ((screenH - rectF.bottom) / getCurrentDisplacement());
```

一个 `MotionObject` 同时持有 x / y / scaleX / scaleY，**线速度天然带进缩放**。scale 交给求解器统一解：

```java
// MotionController :1649-1652（onStart 回调内）

mScaleSolver.addTarget(new MotionObject[]{ mWindowObject });
mMotion.addScaleSolver(mScaleSolver);
dynamicAdjustSpeedAndParam(mWindowObject);
applyReturnHomeSpringParam(mWindowObject);
```

## 7. hook 依据要点（接上一问）

- 经典路径：hook `AnimConstants` 的静态字段 + 硬编码字面量（`0.3f`、`+23.3/+22.0`、`0.25f`、`16000f`、`1.848f`、`1.28f`），入口 `HnLauncherSwipeHandlerV2.getTransSpringInterpolatorX/Y`、`getScaleSpringInterpolatorX/Y`。
- Motion 路径：hook `CloseAnimSceneManager` / `OpenAnimSceneManager` 的实例字段（每次 `MotionController` 构造都会重新读一遍 `:408-419`，所以在构造前后 hook 都有效），或直接 hook `refreshReturnMotionInfo` 改 `mVelocityX/mVelocityY`、hook `ScaleSolver.setScaleTo`。
- 路径开关：`GestureAnimationController.sIsUseMotionEngine`（静态 boolean，反射可写）——可用来强制走经典路径做 A/B 对比。
- V17 `createWindowAnimationToHome` 与 `HnPagedView.onTouchEvent` 反编译失败，涉及它们的 hook 需回 `smali/` 核对。

## 6. 必须说明的限定条件（避免误判）

**不是所有堆叠都能跟手。** `isSupportsInterruption()` 还要求 `!AnimationSinkUtil.localAnimationEnabledV2()`；堆叠的中断类型为 `QUICK_WIN(0)` 或 `SINK(2)` 时，`isSupportsInterruption()==false`，会落到 `HnRecentsView:5104` 和 `TaskViewTouchControllerForStack:146` 的**被拦分支**。所以真正能“动画中点击/滑动立刻响应”的条件是：

```
isStackRecents()  &&  (  isSupportsInterruption()          // 中断型 != SINK 且 localAnimationEnabledV2()==false
                      || isStackAndSupportMotionInterruptAnim() )   // 云控 recents_stack_interruptAnimType == 1
```
另注：堆叠本身在平板/折叠副屏/`isPadOrFullScreen()` 上直接禁用（`:192`）。

### 2.5 与堆叠"即时响应"的关系（两套机制并存）

- **堆叠 touch interruption**（摘要.md §3）：针对**进最近任务（app→overview）** 的入场动画，DOWN 即 `endPlayingAnimForNextResponse()` 杀动画，之后手势/拖卡全速跟手。
- **InterruptAnimationV2**（本文）：针对**返家（overview/app→home）** 与**应用启动**动画，点击被代理成正常 Launcher 点击，动画以 reverse/parallel 方式被打断而非硬杀。
- 两者都要求 `sIsEnableInterruptAnimationV2` 或 `isSupportsInterruption()`，但开关源不同（前者依赖堆叠模式，后者依赖全面屏手势+非 sink）。

# 补充：上滑跟手（未松手）双阶段缩放·位移比例 —— V14 vs V17

## 5.0 结论一句话

两版都是 **"一个 shift 值驱动两段动画"**：`AnimatorControllerWithResistance` 以 **shift=1.0** 为分界——前段 normal（窗口全屏→卡片尺寸），后段 resistance（卡片继续缩小+位移继续）。V14 用单一 `mDragLengthFactor = 屏高/拖动行程` 定义后段终点；V17 在 **Motion 路径**下把"距离阈值"改成 **双行程**（`linearDragLength=1334` / `nonlinearDragLength=1560`），缩放与位移**解耦成两条独立进度**，且缩放由 `ScaleSolver` 物理量驱动而非线性插值。**经典路径两版结构相同。**

---

## 5.1 V14 的双阶段（经典，唯一路径）

### 5.1.1 shift 的产生 — `SwipeUpAnimationLogic.updateDisplacement`（V14 `:108-130`）

```
mTransitionDragLength = getSwipeUpDestinationAndLength()   // = LayoutUtils.getShelfTrackingDistance（两版 LauncherActivityInterface:73-80 完全相同）
mDragLengthFactor     = heightPx / mTransitionDragLength   // initTransitionEndpoints :91，典型 ≈1.5~2.0

shift = displacement / mTransitionDragLength               // :114-117
      （displacement > heightPx 时封顶在 mDragLengthFactor）
if (isTablet) shift /= 2                                   // :119-121
逐帧限幅：Δshift ≤ DRAG_LENGTH_DELTA_FACTOR_MAX = 0.1     // :122-127（防跳变，日志 "change shift from … to …"）
mCurrentShift = shift                                      // 值域 [0, mDragLengthFactor]
```

### 5.1.2 两段的分发 — `setProgress(fMax, mDragLengthFactor)`（`AbsSwipeUpHandler:3215` → `AnimatorControllerWithResistance:69-83`）

| | Stage 1（normal） | Stage 2（resistance） |
|---|---|---|
| 触发 | shift∈[0,1] | shift>1，进度 = `(shift-1)/(mDragLengthFactor-1)` |
| 驱动的 PendingAnimation | `addAppToOverviewAnim`（V14 TaskViewSimulator `:752-758`） | `createRecentsResistanceAnim` FROM_APP（`AnimatorControllerWithResistance:100-132`） |
| 缩放 | `fullScreenProgress` 1→0；`recentsViewScale` **fullScreenScale→1.0** | `recentsViewScale` **1.0→0.5**（`scaleMaxResist`），插值 `DEACCEL` |
| 位移 | `matrixTranslate` 0→对齐偏移 | `TASK_SECONDARY_TRANSLATION` 0→`rectF.top × translationFactor(1.0)`，插值 `LINEAR` |
| 距离含义 | 手指走完 `mTransitionDragLength`（≈到 shelf 的距离）时窗口恰好缩到卡片 | 再走到 `heightPx` 时卡片缩到 0.5（对应进 ALL_APPS 方向的阻力） |

参数表 `RecentsResistanceParams`（V14 `:40-45` ≡ V17 `:46-51`，**完全一致**）：

```
FROM_APP              scaleStartResist=0.75, scaleMaxResist=0.5, translationFactor=1.0
FROM_APP_TO_ALL_APPS  0.75, 0.5, 0.8
FROM_APP_TABLET       1.0,  0.7, 1.0, stopScalingAtTop=true
FROM_OVERVIEW         1.0,  0.75, 0.5
```

> 平板除以 2 只改 shift 映射（手指行程加倍才能到同一阶段），阶段终点比例不变。

---

## 5.2 V17 怎么改的

### 5.2.1 经典路径：结构不变，仅两处加钩

`AnimatorControllerWithResistance.setProgress`（V17 `:75-91`）diff V14：

1. Stage 2 的进度上限不再直接用 `mDragLengthFactor`，而是 `getMaxProgressForMotionController(f2)`（`:93-95`）：**Motion 关 → 原样返回 f2（与 V14 相同）**；Motion 开 → `MotionController.getMotionMaxProgress()`。
2. 新增 `updateRecentsScaleAndTranslationShift`（`:97-114`）：Motion 开时从 `MotionController.mRecentsScaleShift / mRecentsTranslationShift` 取**两条独立进度**，用 `setTagFraction` 分别喂给 normal/resistance controller —— 缩放和位移不再共享同一个 shift。

`createRecentsResistanceAnim`（V17 `:131-205`）diff V14：

- **Motion 关分支**（`:194-196`）＝ V14 原文（同插值器同参数）。
- **Motion 开分支**（`:158-193`）整段重写，见下。

### 5.2.2 Motion 路径：双行程 + 物理缩放（真正的 V17 新"两阶段"）

**行程定义**（`MotionController:354-355`，横屏 `/2` `:522-524`）：

| 量 | 默认值 | 含义 |
|---|---|---|
| `mLinearDragLength` | **1334** | 线性跟手段长度；超过后加 `SpringConstraint`（hertz 8.75，`updateMousePosition :1113-1120`） |
| `mNonlinearDragLength` | **1560** | 缩放归一化分母：`scale = jumpScaleTo(位移 / 1560)`（`:742`） |
| `sMotionMaxProgress` | `(1560×2)/1334 ≈ 2.34` | 替代 `mDragLengthFactor`，作为 resistance 进度上限（`:526`） |

**跟手段的分段折算**（`onSolve :707-712`）：

```
raw = 屏高 - mousePosY - downPosYToBottom
if (raw >= linearDragLength):
    raw' = (raw - linear) × mNonLinearMovementRatio + linear
          // ratio = 7²/(8.75²+7²) ≈ 0.382   （:1093，Mouse hertz=7 / Spring hertz=8.75）
scale = ScaleSolver.jumpScaleTo(max(raw',0) / nonlinearDragLength)
```

即：**前 1334px 全速缩放；超过后每 1px 只算 0.382px** —— 这就是"根据距离两段缩放比例"的物理来源。

**resistance 段的自定义插值**（`AnimatorControllerWithResistance:207-240`）：

```java
// 缩放通道：起止颠倒（卡片→全屏方向的最大缩放），且值来自 ScaleSolver 而非线性
scale:  getMaxScaleForFullScreen → 1.0
        interpolator(t) = (1 - ScaleSolver.getCurrentScaleX()) / maxScaleForFullScreen

// 位移通道：由缩放反推，保证窗口底边贴手指
offsetY: 0 → -(linearDragLength - maxScaleForFullScreen × (windowH - pivotY))
        interpolator(t) = (t'·linear − scale(t')·maxScale·(windowH−pivotY)) / (linear − maxScale·(windowH−pivotY))
```

对照 V14 resistance 段：`1.0→0.5 DEACCEL` + `LINEAR 位移` —— **比例常数（0.5/0.75/1.0）没变，但 V17 把"用什么曲线到达这个比例"从固定插值器换成了跟手距离/物理求解器。**

**缩放与位移解耦**（`updateRecentsScaleAndTranslationShift :97-114`）：

```
mRecentsScaleShift        ≤1 → normal controller 播 scale 通道
                         >1 → resistance controller 播 (shift-1)/(maxProgress-1)
mRecentsTranslationShift  同理独立一条
```

V14 里两者是同一个 `mCurrentShift`；V17 允许"位移已到卡片、缩放还在全屏段"这类错位（Motion 物理引擎自然产出）。

**窗口矩阵里的应用**（`TaskViewSimulator.apply :915-937`，Motion 开时）：

```java
mMatrix.set(motionController.getMatrixByShift(mRecentsScaleShift, recentsViewScroll, …))
// 或 stackrecents 分支 getMatrixByShiftInStack(…, taskViewAnimScale)
```

即 Motion 路径下窗口不再走 `positionHelper + recentsViewScale` 经典拼装，改用 `MotionController` 直接给矩阵。

### 5.2.3 跟手 shift 的平滑器也换了

| | V14 | V17 |
|---|---|---|
| 平滑 | 每帧 Δshift ≤ **0.1** 限幅（`DRAG_LENGTH_DELTA_FACTOR_MAX`） | `ShiftSpringAnimation` 弹簧跟随，k=**1191**，ζ=**1.0**，minVC=0.001（`ShiftSpringAnimation:31-43`），云控 `shiftSpringParams` |
| 位移入口 | 直接 `mCurrentShift.updateValue(shift)` | Motion 关：弹簧 setFinalPosition；Motion 开：`MotionController.dispatchTouchEvent`（`SwipeUpAnimationLogic:167-196`） |

## 0. 结论速览

| 场景 | V14 | V17 |

核心机制：**抽屉可见性（`isAppsViewVisible()`）与 `LauncherState` 是两套独立体系**；`goToState(NORMAL)` 不改变抽屉/负一屏 overlay 的可见性。

---

## 1. 核心机制：两套独立体系

### 1.1 LauncherState 不承载抽屉/负一屏

`LauncherState` 枚举（V17 `com/android/launcher3/LauncherState.java`）：

| 状态 | ordinal | 说明 |
|---|---|---|
| `NORMAL` | 0 | 桌面主屏 |
| `ALL_APPS` | 5 | 存在，但抽屉打开时 LauncherState 可能仍是 NORMAL |
| `BACKGROUND_APP` | 6 | App 在前台时桌面所处状态 |
| `OVERVIEW` | 2 | 最近任务 |

**关键**：抽屉（AllAppsContainerView）是 workspace 上层的 View，不是独立 State。抽屉打开时 `LauncherState` 可能仍为 `NORMAL`；负一屏（HiBoard）是插件 overlay 窗口（`HiBoardClientManager.openOverlay/closeOverlay`），完全不在 `LauncherState` 枚举里。

### 1.2 `goToState(NORMAL)` 不关抽屉/负一屏

返家状态机无条件 `goToState(NORMAL)`：

- **V17** `OtherActivityInputConsumerEx.setStateToNormal()`（`:1671-1683`）：
  ```java
  LauncherState state = launcher.getStateManager().getState();
  LauncherState launcherState = LauncherState.NORMAL;
  if (state != launcherState) {
      launcher.getStateManager().goToState(launcherState, false);  // 无条件 NORMAL
  }
  ```
- **V14** 同名方法（`:1471-1483`）逐行相同（`HnLauncherState.NORMAL`）。
- `GestureAnimationController.endReturnHomeAnim`（V17 `:1651-1695`/V14 `:687-699`）同样无条件 `goToState(NORMAL, false)`。

`goToState(NORMAL)` 恢复的是 workspace 的 alpha/scale（`WorkspaceStateTransitionAnimation` 的 view 列表含 `getAppsView()`），**不改变抽屉 visibility**。抽屉 visibility 只有补丁点才置 GONE。

## 2. 负一屏（HiBoard）：确定性保留

两条主返家路径各有**已证实的结构性跳过**——"从负一屏开 App 返家→回到负一屏"在代码上是**必然**。

### 2.1 三键 Home 路径：`doMainActionIntent` 结构性不关

`Launcher.onNewIntent` → `doMainActionIntent`（V17 `:5088-5111`）：

### 2.2 手势上滑路径：`closeOverlay` 对负一屏跳过

**手势起点**（`OtherActivityInputConsumer.notifyGestureStarted` → `AbsSwipeUpHandler.onGestureStarted:1434` → `LauncherActivityInterface.closeOverlay:261-282`）：

打断动画时图标容器缩放——是连续还是突变
endReturnHomeAnim()	点其他图标 / 触摸桌面 / 文件夹	有意急停——animator.end() / Motion.end() 跳到终值，V14/V17 语义相同
打开动画被底部上滑打断	app 打开中上滑	无可见跳变——FloatingIconView 先 removeView 再 recycle()（scale→1 已不可见），断点 scale 由 mBreakScaleSolver(curScale…) 接管

打断的瞬间，图标容器（workspace）的缩小被停住（冻结在当前值），不会继续缩小，也不会立即跳回 1.0。
机制
打开动画期间——图标容器缩小由 mBackgroundScaleSolver 驱动，目标是 sBackgroundScale（约 0.9/0.83），逐帧写到 mWorkspaceObject / mHotseatObject / mNormalObjects（MotionController.java:4024-4032 设目标，:1797-1819 逐帧写 scale）。
底部上滑打断——走 initAndStartBreakMotion()（MotionController.java:918）：
:947 调 cancelLaunchAnim(false) → setNeedContinuePlay(false)（GestureAnimationController.java:1228-1235）；
AppLaunchMotionAnim 帧监听在 mNeedContinuePlay=false 后停止写入（:1542/:1552/:1732），mBackgroundScaleSolver 的弹簧不再更新 → 缩小冻结；
break motion 只建了窗口对象的 mBreakScaleSolver（当前窗口 scale → 1.0，MotionController.java:987-995）和 mBreakSpringConstraint（hertz=12/damping=0，:1035-1048）——没有把 workspace/background solver 加进 break motion，也没有 reset workspace scale。
所以打断后：窗口弹回全屏（有动画），图标容器停在打断那一刻的缩小值（无动画、无跳变）。随后返家/进最近任务路径接管时才把 scale 写回（如 buildReturnMotion 设回 scaleInterBySwipe，或并行路径直接 setScaleX(1.0f)，MotionController.java:4058-4060）。
对比
不打断：workspace 平滑缩到 sBackgroundScale；
打断：workspace 冻结在中间值，等后续状态机恢复到 1.0——视觉上是"缩小停住了"，不是"突然停止动画跳变"，因为冻结点就是打断瞬间的当前帧值。
V14 经典路径同理：cancelLaunchAnim 只停 launch animator，不碰 workspace scale；V14 无 mBackgroundScaleSolver，workspace 缩放挂在 AnimatorControllerWithResistance 的 app-open animator 上，cancel 后同样停在当前帧。


A. 首次打开应用时，底部上滑"没反应"的可能原因
首次打开 = 冷启动，存在一个*"点击已发出、RemoteAnimationTarget 尚未回来"的空窗期*。这段时间里打断/返家链路的关键门禁全部关闭：
1. canBreak() 空窗 —— 最核心门禁
GestureAnimationController.canBreak()（:975-999）要求：
- mLaunchAnimation != null（冷启动空窗期内为 null）
- 且 animProgress > sIconAnimationAlphaEndPoint（正常 0.06 / lite 0.2，AppLaunchAnimation.java:200-201）
mIsCanBreak 也是到 onMotionAnimationStart 才置 true（AppLaunchMotionAnim.java:1380），动画结束置 false（:1444）。
空窗期内 canBreak()=false → 底部上滑即使被 OtherActivityInputConsumer 收到，startBreakAnimation 会在 :514 直接 return（iAppLaunchAnimation==null 或 !isCanBreak()）。
2. isLaunchAnimRunning() 同样为 false
isLaunchAnimOpenRunning()（:637-640）要求 mLaunchAnimation != null && getNeedContinuePlay() && isCanBreak()。Motion 路径下 OtherActivityInputConsumerEx.getReturnHomeRectF:1359 用它判断：
// Motion 开启时：z = GAC == null || !isLaunchAnimRunning()
空窗期 z=true，返家用 rect 退化为全屏，跟手视觉"没跟起来"。
3. ACTION_DOWN 时标记丢失
OtherActivityInputConsumer.java:299-307：仅在 DOWN 时若 isLaunchAnimRunning() 才置 mIsLaunchAnimRunningWhenSwipeUp=true。冷启动时 DOWN 落在空窗期 → 标记不置 → 后续动画启动后不知道"用户已经在滑"。
4. PreStartAnim / 预备动画路径的干扰
- isSupportLaunchAnimPreparing 开启时走 AppPreStartAnimation（QuickstepAppTransitionManagerImpl.java:3332），它被设为 mLaunchAnimation，但其 isCanBreak() 行为与正式动画不同；
- isNeedEarlyGestureRecentsTrans（OtherActivityInputConsumer.java:951-962）：DOWN 时若 pre-anim 在播或 getAppLaunchAnimStatus()==false（空窗期正是 false），会把 gestureRecentsTransitionWhenMove 置 false → 早期手势返家路径被关。
5. 触摸被"预备态"的 AdditionalClick 消费（非手势区时）
若 DOWN 不在手势区（TouchInterationManager.java:1518），且 isAdditionalClickEvent（:2916）满足条件（getAppLaunchAnimStatus() 空窗期为 false → 通常不成立，但 pre-anim 结束瞬间 status 已 true 时可能成立），会走 AdditionalClickInputConsumer 而非手势消费。
6. 系统侧：recents animation 未 start
底部手势要生效，SystemUI 侧需已 startRecentsActivity/task 可见。冷启动时 onTaskAppeared 迟到 → 桌面拿不到 leash → 整个 gesture handler 未挂上 → 上滑只是普通窗口外触摸，无视觉反馈。
小结（无反应）：主因是冷启动空窗期内 mLaunchAnimation==null / canBreak()==false / isLaunchAnimRunning()==false 三重门禁 + DOWN 时标记未置 + pre-anim 关闭 early gesture。验证时可在 canBreak()、isNeedEarlyGestureRecentsTrans、OtherActivityInputConsumer:299 打时间戳 log。




swipe-up → 小窗/分屏 判定阈值
热区 = 位置判定（椭圆），无速度阈值。链路：OtherActivityInputConsumer.onMotionEvent(MOVE) → OneStepWindowMgr.motionEventMove → changeState(x,y) → isInRegion（OneStepWindowMgr.java:898-934）：
核心阈值（OneStepWindowMgr.java:978-979）：
mShapeHotX = 屏宽 × 0.5，mShapeHotY = 屏高 × 0.55
分屏热区（左上角椭圆，OneStepWindowMgr.java:930）：x²/(0.5W)² + y²/(0.55H)² ≤ 1 → IN_SPILT_HOT
小窗热区（右上角椭圆，OneStepWindowMgr.java:922）：(x−W)²/(0.5W)² + y²/(0.55H)² ≤ 1 → IN_FLOAT_HOT

任务 1：掉帧原因（swipe-up 跟手阶段「打断动画」不掉帧 vs 普通情况掉帧一段时间）
根因是打断路径复用了“热”的动画管线，普通路径要一次性支付整套冷启动成本：
打断动画时（不掉帧）——触摸落在一个正在运行的动画会话上：
- RemoteAnimation 会话、app 窗口的 SurfaceControl leash、TaskViewSimulator（AbsSwipeUpHandler.java:429/790）全部已建好且每帧都在提交 transform；
- RenderThread/Choreographer 已在满帧率运转，launcher 已处于 HnBackgroundAppState（或状态切换已发生），workspace 无需重排版；
- 手势路径的类已加载、JIT 已热。打断只是 cancel 现有 animator、把已有 leash 的 transform 重定到手指坐标——纯廉价逐帧运算。
普通情况（掉帧一段时间）——从静止 app 首次上滑，第一帧前要串行支付：
1. 会话冷启动：TouchInteractionService → 新建 OtherActivityInputConsumer → 经 SystemUiProxy binder IPC 启动 RecentsAnimation（system_server 建 leash、冻结 app、SF 大事务）；
2. 状态切换重排版：进入 HnBackgroundAppState → workspace 重布局，mRecentsView.onGestureAnimationStart()（AbsSwipeUpHandler.java:912-913，源码里专门包了 TraceController.traceBegin("onGestureAnimationStart")——官方自己都知道这段重）重绑任务列表 + TaskViewSimulator 初始化；
3. 首次热身：手势路径类加载 + 解释执行/JIT 编译、图标/缩略图缓存回填。
所以掉的不是某一帧，而是热身期的一段时间——1、2、3 逐步完成后帧率恢复；而打断路径三者全部免单。这解释了“原版就有这个问题”：是 quickstep 架构的固有冷启动成本，V14/V17 都一样。

3. V17 的“全局”其实只是一个条件差：V17 横滑拦截路径不查 mIsTouchOnChildCached（仅长按编辑路径用）；V14 对应位置被 isPosOutView(mHnControlCenterHeader) 挡死。放开这一个子条件 = 等效 V17。
